# Task Tracker Architecture (Strategy C: Targeted Context)

## 1. What the app does

Task Tracker is a FastAPI API for managing tasks. From the files read, it supports health checks plus task create, list, retrieve, update, and delete operations, with filtering by status, priority, overdue state, and tag.

## 2. Data model

Primary entity: `Task`.

Important fields visible from `app/models.py`:

- `id`: string task identifier, generated when stored.
- `title`: required on create; trimmed; cannot be blank; max 200 characters.
- `description`: optional string; defaults to empty string on create.
- `status`: enum: `ToDo`, `InProgress`, `Done`; defaults to `ToDo`.
- `priority`: enum: `Low`, `Medium`, `High`; defaults to `Medium`.
- `assignee`: optional string.
- `due_date`: optional date.
- `tags`: list of strings; trimmed; max 5 tags; no blank tags; each max 30 characters.
- `is_overdue`: boolean response field, computed by storage/business rule logic.
- `created_at` / `updated_at`: datetimes generated by storage.

Models visible: `TaskCreate` (request model for task creation), `TaskUpdate` (request model for partial updates), `TaskResponse` (response model returned by the API).

## 3. Request flow

When a user creates a task, the `POST /tasks` route in `app/main.py` receives a `TaskCreate` payload. Pydantic validates and normalizes the payload according to `app/models.py`, including title and tag validation. The route calls `storage.add_task(payload)`. In `app/storage.py`, `add_task` generates a UUID string, sets `created_at` and `updated_at` to the current UTC time, computes `is_overdue`, creates a `TaskResponse`, stores it in the module-level `_tasks` dictionary, and returns the created task with HTTP 201.

## 5. Conventions

Validation: Request and response models forbid unknown fields. Titles and tags are validated in Pydantic model validators. Invalid enum values are handled through typed enum fields, but exact framework error payloads are not visible from the files I read.

Storage: Tasks are stored in a module-level in-memory dictionary named `_tasks`. IDs are UUID strings. Storage is not visibly persistent beyond process memory.

Error handling: Missing tasks produce `HTTPException` with 404 in route handlers. Invalid status transitions are delegated to `validate_status_transition`, but the allowed transitions are not visible from the files I read. Validation failures are expected from model validation, but exact response shape is not visible from the files I read.

Frontend/backend interaction: CORS allows `http://127.0.0.1:5500` and `http://localhost:5500` with GET, POST, PATCH, DELETE, and OPTIONS. The actual frontend implementation is not visible from the files I read.
